# All repository governance rollout

Status: implementation authorized by the workspace owner on 2026-10-04.

## Objective and acceptance

Adopt one reconstructible workspace-governance distribution across all local
repositories, preserving stronger consumer authorities and required evidence.
Retain the existing logical source `workspace/policy-kit`; Tet4D contributes
portable machinery and remains a consumer.

Acceptance requires a locked canonical distribution; universal governance
without invented Python application metadata; one source for shared skills;
guarded, repeatable adoption; actual runner integration; accepting/rejecting
cases; and an aggregate audit reporting failures, unsupported consumers,
unverified product evidence and scan gaps explicitly. Inventory, installation,
structural checks and accepted adoption are different evidence states.

## Scope and boundaries

The private machine registry derives from the 2026-10-04 reachable census.
Separate repository identity from checkout identity; retain aliases, nested
independent repos, orphaned markers and inaccessible paths. Private absolute
paths, raw transcripts and consumer snapshots stay outside this repository.

Maintained projects receive direct adoption. Worktrees inherit a repository
release and are audited individually. References select a reference profile.
Dependencies, package caches and application-owned stores receive external or
parent-managed checks. Recorded experiments and backups preserve bytes; govern
their external records and producing workflows. No mode is a silent skip.
Unresolved coverage prevents a complete fleet claim.

Protected training inputs stay read-only. Adoption creates no local Python
venv, model downloads, training run, product-semantic rewrite or GitHub
publication. Existing expensive/platform evidence remains required; missing
results remain unverified.
